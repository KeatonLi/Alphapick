# AlphaPick SDD 规格索引

> 本目录是项目的**规格体系**（Specification-Driven Development）。
> 需求总览见 `../system-requirements.md`；闭环验收见 `../quantforge-closure-test-cases.md`。

## 编号体系

| 前缀 | 模块 | 规格文件 |
|---|---|---|
| AUTH | 认证与权限 | `auth.md` |
| DATA | 数据采集与归一化 | `datasource.md` |
| REC | 推荐生成与策略评分 | `recommendation.md` |
| TRK | 收益跟踪与统计 | `tracking.md` |

编号规则：`<前缀>-<三位序号>`，如 `REC-001`。序号全局递增，不随删除复用（保证历史可追溯）。

## 规格项格式

```markdown
### REC-001 规格标题
- 状态：✅ 已实现 / 🔶 部分实现 / 📌 待开发 / ❌ 已废弃
- 需求：这条规格要满足的业务规则（一句到几句）
- 验收标准（可断言）：
  - [ ] 行为 A（对应的测试/验证方式）
  - [ ] 行为 B
- 测试：`backend/tests/test_strategy_service.py::test_db_snapshot_candidate_gets_high_source_quality_and_readable_reason`
```

- 状态与勾选必须与代码和测试**一致**，不一致视为规格失配（SDD 要求修复）。
- 验收标准是给开发者的断言清单，写清"什么算通过"。

## SDD 开发工作流

任何功能开发/修改都按以下顺序：

```
1. 规格先行    新增或更新规格（编号 + 需求 + 验收标准），状态标记
2. 测试驱动    按验收标准写测试（先红）
3. 实现        实现功能让测试变绿
4. 收尾        更新规格：状态 ✅、验收标准勾选、测试映射补齐
5. 回归        跑全套测试 + 规格自检（index 中无失配）
```

原则：

- 没有对应规格的代码改动不落地（先改规格再改代码）
- 没有验收标准的规格不实现（先定义"什么算通过"再动手）
- 测试是规格的执行证据，规格是测试的意图说明

## 规格自检清单

每次提交前检查：

- [ ] 新功能都有规格编号
- [ ] 所有规格状态与代码一致（✅ 表示已实现且测试通过）
- [ ] 验收标准可执行（不写"应该正常"这类模糊词）
- [ ] 测试映射存在（`tests/` 下的真实路径）
